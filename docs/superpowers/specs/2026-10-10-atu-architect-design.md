# ATU 架构设计入口

状态：已确认。用户已确认独立调用与 PRD 自动判断两种入口，并授权先提交已有精简改动，再实现；实施直接使用源码仓库 main。完成后推送到 https://github.com/ATU531/atu-workflow。

## 目标与范围

在新系统或重要架构变化拆 specs 前形成可确认、可引用的整体架构。新增 `$atu-architect`，不恢复已精简的工程角色，不增加默认独立审计轮次，不改变显式 `$atu-quick` 路由。

流程：PRD／需求与仓库证据 → 架构方案 → 用户确认 → `$atu-prd` 功能规格 → `$atu-ai` 实施。

## 触发与职责

- 主动调用始终可以分析和设计；普通改动可输出简短复用结论。
- PRD 在功能拆分前判断：新系统，重大模块/共享契约/数据所有权/事务/部署边界变化，或需要架构取舍的质量目标。
- 大量页面、多个任务、支付或权限类别本身不是架构触发器。已存在适用且已确认的架构则引用，不重新生成。
- 架构阶段写项目 `docs/architecture/`（或明确指定的设计位置）；PRD 仍只写 `specs/`，角色切换及写入边界须明确。

## 产物与质量

每个系统或变更范围默认一份文档。建议路径 `docs/architecture/<scope>.md`，包含版本、范围、需求来源、确认依据；事实、已确认约束、建议与未决问题分开。

内容按问题需要组织：目标/约束、现状和目标模块边界、依赖方向、数据归属和一致性、关键成功/失败流程、关键技术取舍、可验证的扩展场景、分阶段演进/兼容/回退。未知容量不虚构数字，已有系统先检查真实代码，架构不替代 UI 设计稿及其确认。

设计模式参考按需读取，说明实际问题、简单方案、所选模式、代价、验证方式；不默认引入微服务、DDD、CQRS、消息队列或多层抽象。不复制完整教程，不产生实现任务或第二套功能依赖图。

## 确认与接入

- 用户确认前为 DRAFT，不因 PRD 已确认而自行批准架构；关键决定集中确认。
- 已批准内容不被未确认修改覆盖；后续草案放同文档的新版本小节，保留旧版本及确认记录。版本只在确认后成为适用基线。
- 架构属于补充技术约束，不是业务需求源。目录发现排除架构作为 PRD；显式单 PRD 仍可附带加载适用架构约束，不能借此扩充业务范围。
- PLAN 来源账本和功能 design.md（快速规格在复用契约段）引用路径、批准版本和适用决定/小节，不再新增账本。
- 架构变更通过现有 PRD change-mode 更新受影响规格；S1 检查所引用版本是否仍适用，S2 遵守批准目标而非一概维持旧代码，S3 在现有合并检查中核对边界。
- 旧项目没有基线文档，不因此全局阻塞；发现当前任务确需尚未确认的架构决策时，只阻塞受影响工作。

## 验证与交付

验证主动调用、自动前置、已有架构复用、普通功能不误升级、未确认决策不进入最终任务、版本变化只影响相关功能、强制快速入口保持原行为。

结构检查证明入口与引用打包完整；独立行为回放验证路由与产物，不把关键词匹配当成行为证明。更新源码和现有独立 Skill 安装副本，校验一致性；新会话真实发现保留为明确的实际验证边界。
