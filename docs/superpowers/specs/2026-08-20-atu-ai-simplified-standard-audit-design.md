# ATU AI 标准审计精简设计

## 目标

在不削弱真实安全边界、授权边界和证据真实性的前提下，把 `$atu-ai` 标准执行从 N1–N8 的逐任务高强度审计，压缩为 S1–S4 的按功能合并验证，减少重复读取、重复检查、账本写入和恢复仪式。

## 当前问题

- 标准路径需要加载 `standard-workflow.md` 和八个节点文件，正文约 7000 词。
- 每个任务都执行独立规格审查、独立质量审查和独立 QA，并在修改后从前序门禁重跑。
- 应用快照与 `spec_contract` 双重哈希在多个节点重复计算。
- `verification.md` 在 N1、N3、N4、N6、N7、N8 反复同步。
- 缺少账本字段或哈希不匹配会触发任务 reopen 和完整恢复链，即使当前规格、代码和测试可直接重新验证。

## 新流程

### S1 边界确认

一次性读取授权规格、适用仓库规则、当前 Git 状态、依赖和阻塞项。选择一个功能和一个当前任务，保护用户已有改动。只有真实未决决定或缺少当前任务必需环境时停止。

### S2 测试驱动实现

每次只实现一个任务。保留最小 RED、最小实现、聚焦 GREEN 和必要附近回归。任务间有依赖或写入重叠时串行；不为每个任务启动独立审查或 QA。

### S3 合并验证

在功能准备收尾时，对完整功能 diff 执行一次合并验证：相关测试、项目已有静态检查、自审和逐项验收矩阵。修复后只重跑受影响检查以及最终必要回归。

普通标准任务不默认启动独立上下文。以下关键风险需要在功能级别增加一次独立代码审查：

- 认证或授权边界；
- 支付、资金或权益结算；
- 破坏性或不可逆数据迁移；
- 有真实消费者的公共 API 兼容契约；
- 已获授权的生产变更。

独立 QA 仅在验收依赖真实浏览器、设备、支付方、外部服务、人工作业，或用户明确要求时启用。不可用的必要证据仍必须标记 `NOT RUN`、`MANUAL REQUIRED` 或 `BLOCKED`，不能用 mock 替代真实边界。

### S4 收尾与恢复

验证通过后更新任务勾选、PLAN 状态、必要文档和简短证据。`verification.md` 仅在跨会话、多任务或项目明确要求持久证据时创建或更新，默认在功能收尾写一次。

恢复时重新读取规格、任务状态、Git 状态、当前 diff 和已有验证记录。规格或代码已变化时重新执行受影响的 S2/S3，不因缺少旧哈希自动撤销已完成任务。仅在任务完成标记与当前可观察证据发生实质冲突时，报告冲突并请求方向或重新验证。

## 删除和保留

删除：

- N1–N8 节点文件和节点跳转合同；
- `spec_contract` 哈希；
- 每节点应用快照哈希；
- 默认独立规格审查；
- 默认逐任务独立质量审查和 QA；
- 强制原子 reopen 恢复链；
- 每节点 `verification.md` 同步。

保留：

- 已批准规格是实现合同；
- 用户改动保护和精确作用域；
- RED → GREEN 与相关回归；
- 真实证据状态；
- 凭证、生产数据、破坏性操作和外部写入的授权边界；
- 提交、推送、部署、迁移和发布必须单独获得授权。

## 预算与验收

- `$atu-ai` 主入口、标准工作流和 S1–S4 引用合计不超过 3000 个空白分词。
- 标准路径只暴露 S1、S2、S3、S4 四个阶段，不再引用 N1–N8。
- 普通标准场景只需功能级合并验证；关键风险最多增加一次独立代码审查。
- 快速模式和 `$atu-quick` 的既有行为不变。
